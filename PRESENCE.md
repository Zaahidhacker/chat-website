# Last seen and connection presence

Online now requires both membership in the private `universe-presence:two` Presence channel and a server-generated last_seen timestamp less than 65 seconds old. Recent database activity alone never claims Online. Only visible pages with activity sharing enabled publish presence; backgrounding, sign-out and privacy changes withdraw it. Multiple tabs/devices combine, so one hidden tab cannot make another visible tab offline. Updates serialize and retry transient failures twice; reconnect generations prevent stale acknowledgements from cancelling a new subscription.

No extra heartbeat polling was added. Existing visible-only receipt heartbeats maintain last_seen, and a guarded, parameterless `universe_presence_leave()` RPC stamps the current user's departure and clears typing. Its fetch uses keepalive as a best effort during page closure. Displayed dates and times use Asia/Colombo, with explicit Sri Lanka time in the title. Privacy-off, missing timestamps, offline viewers and implausible future timestamps never show a green online dot.

A browser/OS can suspend a process before departure can be sent, and abrupt network loss cannot be detected instantly. The server-timestamp lease and existing 15-second UI clock bound a stale online indication to about 65–80 seconds when no further activity arrives. This is website presence, not a claim that someone is reading or physically using their phone. Both devices need to refresh after this deployment; older clients do not publish the new presence signal.

The channel uses private mode and two member-only RLS policies on realtime.messages, limited to the exact topic and Presence extension. Supabase separates public and private channels even with identical topics, so unrelated public channels retain their existing behavior. See [Realtime concepts](https://supabase.com/docs/guides/realtime/concepts) and [Authorization](https://supabase.com/docs/guides/realtime/authorization). The leave RPC intentionally uses SECURITY DEFINER because clients cannot update member metadata directly; it checks membership, uses auth.uid() rather than client input and pins an empty search_path. Anonymous execution is revoked, outsider calls are denied. The advisor's [authenticated function execution notice](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) is expected for this guarded API.
