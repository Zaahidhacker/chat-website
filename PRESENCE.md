# Foreground presence and last seen

Online means that at least one of the person's tabs/devices is publishing visible-foreground presence to the private room. Reading messages, opening settings and using games all keep it active without typing. Live foreground presence is independent of the last-seen timestamp, including stale or missing timestamp metadata. A recent timestamp alone never implies Online. The activity-sharing privacy switch is respected everywhere.

Hiding the website or switching to the phone home screen untracks presence immediately. A normal browser closure removes the socket's presence. The observer records the departure locally, clears typing and shows Last seen immediately, even if the database departure RPC is delayed. This explicit departure overrides queued typing updates. Returning to a visible page republishes presence and clears the departure. Multiple tabs combine; one hidden tab cannot take another visible tab offline.

The initial Presence sync may arrive before the subscription acknowledgement. It is retained rather than reset on SUBSCRIBED. A channel error clears connection knowledge until a new sync arrives. Existing visible-only receipt heartbeats maintain persistent last_seen, and the guarded universe_presence_leave RPC stamps departure and clears typing using best-effort keepalive. Displayed times use Asia/Colombo. No new constant polling, schemas, personal records or subscriptions were introduced.

Browsers usually deliver visibility/pagehide events promptly, but force-killing an app, losing the network or OS suspension can prevent a final signal. Those cases require server socket-disconnect detection and cannot be guaranteed instantaneous by a website. Foreground visibility also does not establish which particular message someone is reading.

The channel uses private mode and two member-only RLS policies on realtime.messages, limited to the exact topic and Presence extension. Supabase separates public and private channels even with identical topics, so unrelated public channels retain their existing behavior. See [Realtime concepts](https://supabase.com/docs/guides/realtime/concepts) and [Authorization](https://supabase.com/docs/guides/realtime/authorization). The leave RPC intentionally uses SECURITY DEFINER because clients cannot update member metadata directly; it checks membership, uses auth.uid() rather than client input and pins an empty search_path. Anonymous execution is revoked, outsider calls are denied. The advisor's [authenticated function execution notice](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) is expected for this guarded API.

## Typing and reconnect correction — November 3, 2026

An unexpired, server-issued typing signal now also proves active presence, even if the separate private Presence channel is temporarily unavailable or last_seen is stale. It requires a connected viewer, respects share_presence, rejects implausibly distant future typing timestamps, and expires at the server typing deadline. Departure clears typing as before. A fresh last_seen timestamp alone still does not imply Online.

Client recovery now retries failed metadata catch-up at bounded 1/3/8-second delays instead of relying only on the 30-second heartbeat. Healthy connections do not gain continuous polling. Restoring a persisted browser page reopens its realtime subscriptions. Successfully received events clear stale connection-error indicators.

## Foreground correction — November 3, 2026

Foreground room membership now takes precedence over timestamps and typing. Observed departures suppress delayed typing signals until a foreground join returns. This supersedes the earlier 65-second timestamp prerequisite and the typing-only fallback described in historical verification notes. Six new two-client scenarios cover state-before-ack delivery, idle reading, settings, actual game interaction, stale metadata, delayed departure RPCs, home/return, tab closure, multiple tabs and privacy.
